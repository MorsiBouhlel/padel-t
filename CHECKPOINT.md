# Checkpoint — Tournois de padel

Dernière mise à jour : 2026-10-27 (PR #1 `feature/new-design` fusionnée dans `main` (`6174058`), `main` à jour en local, tout déployé en production ; départage inchangé, voir `standings` dans `lib/logic.js`)

## Où on en est

Application web mobile-first de gestion de tournois de padel, **en production** sur https://pt.algoris.tn.
Tournoi en cours : **Bajada Championship 4 Edition** (12 paires, 66 matchs, importé de Score7, 6 matchs joués au moment de l'import).
Lien public : https://pt.algoris.tn/#/t/cd1b9683d0

## Fonctionnalités en place

- **Format** : championnat en poule unique (aller simple, 3 pts victoire / 0 défaite, 4 qualifiés), puis play-offs (demi-finales 1er–4e et 2e–3e, finale, match pour la 3e place). Aussi possible : plusieurs poules, aller/retour.
- **Départage** : points, différence de jeux, jeux marqués, confrontation directe (égalité à deux), moins de matchs joués, puis ordre d'inscription (pas de vrai tirage au sort).
- **Scores** : 3 sets max, forfait (6-0 6-0), double forfait (défaite pour les deux), correction/effacement.
- **Calendrier** : génération (jours, horaires, terrains) ou dates par match.
- **Report de match guidé** (idée 2) : limite = veille de la journée suivante, confirmation pour une exception, historique, filtre « Reportés », compteur de reports par paire.
- **Page par paire** (idée 6) : `#/t/<slug>/team/<id>` avec stats, forme, prochains matchs, résultats.
- **Pénalités de points** par paire (ex. changement de partenaire : 2 pts), saisie manuelle.
- **Paiements** (idée 13) : onglet organisateurs seulement, 150 DT/joueur (réglable), paiements partiels, export CSV. Jamais exposé publiquement.
- **Comptes organisateurs multiples** : propriétaire `admin` + autres comptes créés depuis « Mon compte ». Tous gèrent tous les tournois.
- **Alertes de retard / forfait** (idée 1) : `lateState` dans `lib/logic.js` ; badge « En retard » (date dépassée) ou « Forfait à appliquer » (journée suivante commencée), filtre « En retard », bandeau + bouton organisateur `POST /api/tournaments/:id/apply-forfeits` (double forfait 6-0/6-0, jamais automatique). Fuseau Africa/Tunis. Aucun match concerné aujourd'hui (24 matchs sur 66 ont une date).
- **Changement de partenaire** (idée 4) : bouton organisateur sur la page de la paire, `POST /api/teams/:id/partner-change`. Refusé hors championnat (avant démarrage : modifier les joueurs directement ; play-offs : 409). Pénalité par défaut 2 pts à partir de la journée 4 (journée en cours = plus avancée parmi matchs joués ou datés ≤ aujourd'hui), modifiable dans le formulaire. Historique public (table `partner_changes`).
- **PWA** (idée 8) : `manifest.webmanifest`, icônes PNG (générées en Node, balle sur fond vert), `sw.js` (réseau d'abord, `/api/` jamais mis en cache). Installable depuis le navigateur du téléphone ; validée sur téléphone.
- **Sauvegarde auto** (idée 10) : `VACUUM INTO` au démarrage puis toutes les heures (1 fichier/jour, fuseau Tunis, 14 conservés) dans `/data/backups`. API `GET/POST /api/backups`, `GET /api/backups/:name` (propriétaire seulement) ; boutons dans « Mon compte ». Déployé.
- **Export WhatsApp** (idée 11) : boutons dans Classement (texte + image PNG générée en canvas) et Matchs (prochains matchs + retards, en texte). Côté navigateur uniquement (`public/app.js`, section « Export WhatsApp »), aucune route serveur. Texte testé en Node ; image canvas et partage natif validés sur téléphone. Déployé.
- **Agenda .ics** (idée 7) : `GET /api/t/:slug/calendar.ics[?team=<id>]` (public), `lib/ics.js`. Matchs datés avec 2 équipes connues ; horaire "18:00"/"18h30" → événement de 1h30 (Tunis = UTC+1 converti en UTC), horaire absent ou libre → journée entière ; score dans la description ; UID stable par match donc les reports mettent l'abonnement à jour. Liens « s'abonner » / « télécharger » dans Matchs et page de paire. Testé (2 tests + API) ; validé sur téléphone. Déployé.
- **Historique des modifications** (idée 3) : table `audit_log`, helper `audit()` dans `server.js`. Journalise avec « avant → après » : scores/forfaits/effacements, planning (date, heure, terrain), reports, réglages du tournoi, ajout/modif/suppression de paire (pénalité, poule), changement de partenaire, tirage, lancement, calendrier généré, play-offs, forfaits appliqués, paiements, import. `GET /api/tournaments/:id/audit` (organisateurs), onglet « Historique » (organisateurs seulement). Ne couvre que ce qui est fait **après** le déploiement ; l'historique supprimé avec le tournoi. Connexions et comptes organisateurs non journalisés. Déployé.
- **Statistiques** (idée 12) : onglet public « Stats » (`statsPanel` dans `public/app.js`, calcul côté navigateur, rien côté serveur) : chiffres clés, meilleure attaque/défense (jeux par match), sets gagnés, séries de victoires (en cours/record), remontées, plus large victoire, match le plus accroché/long. Forfaits exclus des jeux/sets, inclus dans les séries. Testé avec des données API ; validé sur téléphone. Déployé.
- **Édition suivante / archives** (idée 14) : `POST /api/tournaments/:id/next-edition` (organisateurs) crée un tournoi en inscriptions avec les mêmes réglages et règlement, les paires cochées (sans pénalités, poules ni paiements) et `prev_id`. Dialogue « Édition suivante » (bouton dans l'en-tête dès que le tournoi a démarré) : nom incrémenté (4 → 5), la dernière de chaque poule décochée par défaut, avertissement si classement provisoire. Liens ← édition précédente / suivante → sous le titre ; l'accueil sépare « Archives » (tournois terminés). Testé par API ; dialogue et accueil validés sur téléphone. Déployé.
- **Notifications push** (idée 9) : Web Push (VAPID, paquet `web-push`), sans compte. Clés VAPID générées au 1er démarrage dans `/data/secrets.json` (ne pas les perdre : sinon tous les abonnements deviennent invalides). Tables `push_subs` (par tournoi, `team_id` NULL = tout le tournoi) et `push_sent` (anti-doublon). Routes publiques : `GET /api/push/key`, `POST|DELETE /api/t/:slug/push`, `/push/status`, `/push/test`. Envoi via `notify()` dans `server.js` (résultat saisi, corrigé ou annulé, changement de planning d'un match non joué, report, forfaits appliqués, play-offs lancés) ; `runReminders()` toutes les 10 min (veille 18h, 2 h avant, en retard, forfait à appliquer, fuseau Tunis), textes et règles dans `lib/notify.js` (8 tests). Service worker : `push` et `notificationclick`. Le bouton 🔔 est mis en avant (« Activer les notifications ») tant que l'appareil n'est pas abonné au tournoi, puis affiche « Notifications ✓ » (`updateNotifButton` dans `public/app.js`). Cloche 🔔 aussi dans la barre du haut (`#bell`, point jaune tant que non abonné). Notification de bienvenue au premier abonnement d'un appareil à un tournoi (pas au changement de paire suivie). Testé par API et tests unitaires ; validé sur téléphone (iPhone : exige l'appli installée sur l'écran d'accueil).
- **Notifications prédéfinies** : bouton « 📣 Notifier tout le monde » (organisateurs, en-tête du tournoi). Messages stockés en base (`broadcast_templates`, communs à tous les tournois, installés une seule fois depuis `DEFAULT_TEMPLATES` de `lib/notify.js` : flag `broadcast_seeded` dans `settings`) et configurables via « ⚙ Configurer » (titre + texte ≤ 300 caractères, ajout/suppression, « Rétablir les messages d'origine »). Variables `{journee}` (numéro modifiable à l'envoi) et `{frais}`. Routes : `GET /api/tournaments/:id/broadcasts`, `POST /api/tournaments/:id/broadcast`, `GET/PUT /api/broadcast-templates`, `POST /api/broadcast-templates/reset`. Reçus par **tous** les abonnés du tournoi, y compris ceux qui ne suivent qu'une paire ; même message limité à 1 par minute ; journalisé dans l'historique. Testé par API .
- **Tableau de bord « Suivi »** (organisateurs, onglet avant Paiements) : avancement (matchs joués, journée, prochain match, encaissé, appareils abonnés), matchs du jour, puis « À traiter » : forfaits à appliquer, matchs en retard (jours de retard, limite), matchs à planifier (journée en cours et suivante), paiements en attente, paires sans abonné dédié (`GET /api/tournaments/:id/followers`), 5 dernières modifications. Boutons vers l'onglet concerné (`data-goto`). Calcul côté navigateur (`dashPanel`). Testé avec les données réelles de l'API ; validé sur téléphone.
- **Prévisions « Chances »** (**réservées aux organisateurs pour le moment** : onglet masqué aux invités et `GET /api/t/:slug/forecast` exige la connexion ; pour l'ouvrir au public : retirer `admin` de la route et les filtres `isAdmin()` dans `public/app.js`) (onglet, 6e icône de la navigation du bas ; encart « Ses chances » sur la page d'une paire) : probabilités par paire de se qualifier, finir 1re de poule, atteindre la finale, gagner, finir sur le podium. `lib/forecast.js` : niveau de chaque paire par régression logistique sur les sets joués (pénalité lambda = 4 : prudent quand il y a peu de matchs ; forfaits ignorés), puis 5 000 simulations des matchs restants avec les vraies règles (`L.standings`, `L.knockoutSeeds` — extrait de la route `knockout` —, `L.buildBracket`) ; en phase finale les résultats connus sont respectés. `GET /api/t/:slug/forecast` (organisateurs pour le moment, ~0,8 s, mis en cache tant que les résultats ne changent pas ; graine fixe donc résultat stable). 10 tests dans `test/forecast.test.js`. Avertissement « estimation peu fiable » sous 25 % de matchs joués. Les jeux/scores ne sont pas pris en compte (seulement qui gagne chaque set). Testé par API et banc d'essai de rendu ; validé sur téléphone.
- **Chances par match** (2026-10-27, codé, testé en Node, **ni commité ni déployé ni vu sur téléphone**) : sous chaque match à jouer, les organisateurs voient « Chances 62 % – 38 % » (`winChanceText` dans `public/app.js`, onglets Matchs et Tableau, calcul côté navigateur à partir de `rating` renvoyé par `GET /api/t/:slug/forecast`). Même modèle que « Chances » (niveaux estimés sur tous les sets joués, forfaits ignorés, match en 2 sets gagnants). Réservé aux organisateurs. Première étape de la fonction « parcours vers un objectif » voulue par l'utilisateur (simulation : que faut-il gagner pour viser qualification / podium, d'après les matchs joués) ; il veut du **simple** : prochaine étape à définir avec lui (par exemple chances d'atteindre un objectif). Un premier jet trop détaillé (route `/journey`, victoires nécessaires, match par match) est rangé dans un patch hors dépôt (scratchpad de la session, `parcours-detaille.patch`, peut être perdu).
- **Invitation à installer l'appli** : bandeau jaune sous la barre du haut (`#install`, logique `installBanner` en bas de `public/app.js`). Android/Chrome : bouton « Installer » via `beforeinstallprompt` (le bandeau n'apparaît qu'une fois l'événement reçu) ; iPhone : bouton « Comment ? » qui explique Partager → Sur l'écran d'accueil (et Safari obligatoire). Masqué si l'appli est déjà ouverte en mode installé, ou 14 jours après un « ✕ » (`localStorage.installDismissed`) ; rien sur les navigateurs qui ne savent pas installer. Logique testée par banc d'essai (7 cas) ; validé sur téléphone.
- **Score keeper** (comptage en direct, codé le 2026-10-24, déployé, validé et commité (`d4e18d9`) le 2026-10-25) : **seuls les organisateurs créent le lien** : sous chaque match à jouer (liste Matchs, tableau, page de paire), boutons « ▶ Score keeper » et « 🔗 Lien » (partage du lien aux joueurs, par WhatsApp par exemple) ; les joueurs ouvrent le lien reçu (et peuvent « Reprendre » sur leur appareil). Page plein écran `#/live/<jeton>` pour téléphone sur support : deux énormes boutons +1 (un par paire), annuler le dernier point (↶), score en gros (sets, jeux, points), « Point décisif » / « Tie-break » / « Balle de set/match », écran maintenu allumé (Wake Lock), vibration, anti double-tap (300 ms), conçu pour le **paysage** (mise en page compacte ; verrouillage `screen.orientation.lock('landscape')` tenté, accepté seulement par certains navigateurs ; en portrait, invite « Tournez le téléphone en mode paysage » avec « Rester en portrait », choix mémorisé dans `localStorage.keeperPortrait`) — ajouté, déployé et validé sur téléphone le 2026-10-25. Règles : meilleur des 3 sets, 3e set complet (pas de super tie-break), point décisif à 40-40, tie-break à 7 points à 6-6 dans chaque set, y compris le 3e (confirmé par l'utilisateur le 2026-10-25). Moteur `public/keeper-engine.js` (partagé navigateur/serveur ; le serveur **rejoue la liste des points** et ne fait jamais confiance au score affiché ; 8 tests dans `test/keeper.test.js`). Table `live_scores` (jeton secret, points JSON, statut `live`/`submitted`). Routes : `POST /api/matches/:id/live` (organisateurs : crée le comptage ou renvoie le jeton existant), `GET|PUT|DELETE /api/live/:jeton`, `DELETE /api/matches/:id/live` (organisateurs). Le jeton n'est jamais dans l'état public ; le score en direct l'est (`match.live`). Points gardés en local si hors connexion et réenvoyés ; un 2e téléphone avec le même lien se synchronise (relève toutes les 4 s). À la fin : « Envoyer le résultat » → statut `submitted` ; un organisateur valide (bouton Valider dans Matchs ou carte « Scores à valider » du Suivi = `PUT /api/matches/:id` habituel, qui efface le comptage) ou rejette. Rien ne touche le classement avant validation. Testé par API (scénario complet), banc d'essai Node et sur téléphone (copie du lien comprise).
- **Code score keeper** (2026-10-26, codé, testé par API et déployé) : le bouton « 🔗 Lien » donne désormais un **code à 6 caractères** (`ABC-DEF`, alphabet sans 0/O/1/I/L), colonne `live_scores.code` (unique, ajoutée et remplie pour les comptages existants au démarrage). L'onglet n'apparaît dans la barre du bas que s'il y a au moins une partie en direct (pastille rouge), pour ne pas surcharger la barre ; il se rafraîchit toutes les 5 s quand il est ouvert. - **Photos des joueurs** : table `player_photos` (JPEG 256 px en BLOB, donc incluses dans les sauvegardes). Envoi réservé aux organisateurs (`PUT/DELETE /api/teams/:id/photo/:n`, dans « Modifier l'équipe », envoi immédiat), lecture publique `GET /api/photos/:teamId/:n?v=`. Réduction/recadrage carré faits dans le navigateur (canvas). Testé par API ; **le redimensionnement canvas et l'affichage n'ont jamais été vus dans un vrai navigateur.**
- **Noms de paire** : « A & B » par défaut (facultatif, suit les joueurs tant qu'il n'est pas personnalisé).
- **Import** d'un championnat existant : `POST /api/import`, script `scripts/import-score7.js` (déjà exécuté, ne pas relancer).

## Technique

- Stack : Node 20, Express, SQLite (`better-sqlite3`), front en JavaScript sans build (`public/`). ~1300 lignes.
- Fichiers : `server.js` (API, base), `lib/logic.js` (classement, tableau), `public/app.js` + `style.css`, `test/` (28 tests unitaires, `npm test`).
- Déploiement : Docker (`docker compose up -d --build` dans ce dossier). Données dans le volume `padel-data` (`/data/padel.db`, `/data/secrets.json`).
- HTTPS : Caddy du projet `nextrack` (`/home/nextrack/nextrack/Caddyfile`, bloc `pt.algoris.tn`, conteneur `nextrack-caddy-1`), réseau Docker partagé `edge`. Port 3020 limité à 127.0.0.1.
  - Recharger Caddy : `docker exec nextrack-caddy-1 caddy reload --config /etc/caddy/Caddyfile`
  - Sauvegarde du Caddyfile d'origine : dossier temporaire de session (à ne pas compter dessus).
- Mot de passe du propriétaire : généré au 1er démarrage (`docker compose logs padel`) ; `ADMIN_PASSWORD=... docker compose up -d` le réinitialise.
- Sauvegarde de la base : `docker compose cp padel:/data/padel.db ./backup-padel.db` (contient hachages de mots de passe et paiements : ne pas publier).

## Limites connues

- Les forfaits pour retard ne sont jamais appliqués automatiquement : un organisateur doit cliquer (volontaire).

- Notifications push : abonnement par appareil, aucune notification aux organisateurs seuls.
- Dépôt git : `feature/new-design` poussée sur GitHub (`MorsiBouhlel/padel-t`), `main` pas encore à jour.
